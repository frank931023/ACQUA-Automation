## 1. 要解決的問題

### 現況

ACQUA 的 DUT & Measurement Wizard 跑完之後,會依照勾選的條件把專案樹裡
對應的測項打開。那一組測項是**依測試邏輯**組織的 —— 送話、收話、迴音、
不同頻寬、不同音量。

但那組測項**天生橫跨多個物理擺位**:有的要在無響室、有的在殘響室,
收音距離 1.5 m 跟 2.3 m 是不同的桌台位置。

目前的自動化流程被迫這樣處理:

```
擺位 A 的測項  →  存成 plan 1
擺位 B 的測項  →  存成 plan 2
擺位 C 的測項  →  存成 plan 3
                  ↓
            排成執行序列,中間人工移動機構
```

**問題是這個切法不自然。** Wizard 的輸出不是照擺位分的,硬切會把
同一個測試邏輯的測項拆到不同 plan,而且每次 Wizard 的勾選改變,
整套 plan 都要重新切一次。

### 想要的

**一個 plan 從頭跑到尾,擺位自己切換。**

每個測項在 ACQUA 裡就帶著「我需要哪個擺位」的資訊,跑到它之前
機構自動移動到位,移完繼續跑。

## 2. 關鍵發現:這個機制已經存在

查證過程中最重要的發現 —— **不需要從零發明,ACQUA 的資料模型本來就支援,
而且你的專案已經在用,只是沒人拿它驅動機構。**

### 2.1 每個測項可以帶自訂標籤

存在 `acqua.TreeItems.AdvancedDescription`(每個測項一欄):

```xml
<Properties>
  <UserDefinedProperties>
    <UserDefinedProperty name="Room">RR</UserDefinedProperty>
    <UserDefinedProperty name="DUTType">SHAR</UserDefinedProperty>
  </UserDefinedProperties>
  <HRTSettings/>
</Properties>
```

在 ACQUA UI 裡叫 **Tags**:專案樹右鍵測項 → `Edit Tags`。
樹的 `Keywords` 欄位打開後可以一眼看完整棵樹的標籤。

**實際使用量:**

| 資料庫 | SMD 總數 | 有標籤 |
|---|---|---|
| `51_MS_Teams_Rev05_SP2` | 4304 | **1858** |
| `ACQUA_auto_v2026Aug` | 1477 | 90 |
| MMD 群組(兩個庫) | 577 / 182 | **0** ← 只標 SMD,不標群組 |

### 2.2 既有標籤本來就在描述物理擺位

這是最關鍵的一點。SP2 已經在用的標籤:

| 標籤 | 值 | 這其實是什麼 |
|---|---|---|
| `Room` | AR (1092) / RR (534) | **無響室 / 殘響室** |
| `DUTType` | SHAR / PERS / SH15 / SH23 | **共享/個人空間、1.5m/2.3m 收音距離** |
| `Position` | P1 / P2 | 擺放位置 |
| `snd_distance` / `rcv_distance` | snd_default / rcv_default | 送收話距離 |
| `UseCase` | E2E / DI / PREP / OL | (測試情境,非擺位) |
| `Export to .wav` | Channel 1, Channel 2 | **會驅動行為** —— 見 2.4 |

**`Room` 和 `DUTType` 就是擺位資訊。** 缺的只是把它接到機構。

### 2.3 ACQUA 原生就有「每測項自帶硬體位置」

不只自訂標籤,`TreeItems` 還有兩個原生欄位:

```
TurningDevices    {"TurningDevices":[{"Angle":"-60","DeviceType":"HRT","GUID":"..."}]}
                  SP2 約 676 個測項設了實際轉盤角度(0/-30/-45/-60/-90/45 度)

HHPSettingName    "STD:Default (0,0,0) rel AHP"
                  222 個測項指向具名的話筒定位器設定
```

**這證明「每個測項帶著自己的硬體位置」是 ACQUA 設計裡本來就有的概念。**
我們要做的事跟它同構,只是對象換成天車/桌台。

> ⚠️ ACQUA 會不會**自動執行** `TurningDevices` 的角度,尚未驗證 ——
> 沒有 HRT 轉盤可以測。如果會,那一塊根本不用我們管。

### 2.4 標籤不只是註記,有些真的會驅動行為

`after_each_measurement.py` 裡:

```python
if Tags.Exists('Export to .wav'):
    ... 匯出 wav ...
```

**所以「標籤 → 腳本讀取 → 做事」這條路是現成的生產模式,不是我們發明的。**

## 4. 實測數據:這件事值不值得做

以 `51_MS_Teams_Rev05_SP2` 的 Speakerphone 專案為例(2302 個測項):

```
相異擺位組合                      12–13 種
按專案樹順序跑,擺位變動          41 次
照擺位分組跑,只需切換            11 次
```

假設一次移動兩分鐘:

```
照樹順序    41 × 2 分 ≈ 82 分鐘  純移動時間
照擺位分組  11 × 2 分 ≈ 22 分鐘
```

### 分組會不會拆散相依的測項?

Record → Analy 這類相依在同一個 MMD 內。檢查結果:

```
葉層 MMD(含 2 個以上測項)          134 組
真的含兩種不同擺位的                   8 組(6%)
```

**94% 的測項組本身就是同一個擺位** —— 照組分批安全,只有 8 組要個別處理。

> 📌 **重要規則:沒有標籤 = 沿用當下擺位。**
> 1370 個測項沒有擺位標籤,它們是 prep / stabilize / delay 之類的輔助項。
> 一開始我把「沒標籤」當成一種獨立擺位,算出 283 次切換 —— 那是錯的。

### 要標幾個測項?

**41 個轉折點,不是 2302 個。** 只在擺位改變的那一筆下標籤:

```
測項 001   Setup = RR-SHAR-1.5m     ← 標
測項 002   (不標)                   ← 沿用
   ...
測項 058   Setup = AR-default       ← 標(這裡要換)
```

## 5. 目標架構

### 5.0 ⭐ 定案:在 SMD 明確指定擺位名稱

> **這一節經過兩次翻轉,過程寫在下面。結論是回到最初的做法,但現在有數據支撐。**
>
> | 版本 | 做法 | 為什麼改 |
> |---|---|---|
> | 初版 | SMD 加 `Setup = <擺位名稱>` | —— |
> | 修正一 | 改用既有語意標籤 + 對照表 | ACQUA 做不出同步的下拉選單 |
> | **定案** | **回到 `Setup` 標籤** | **語意標籤資訊不足,見 5.0.2** |

#### 5.0.1 為什麼不能在 ACQUA 裡做下拉選單(這部分仍然成立)

| 查證結果 | 影響 |
|---|---|
| ACQUA 的 Tag 編輯器是**自由輸入** | 打錯字會靜默對不上 |
| 沒有「允許值清單」的機制 | DB 裡沒有這種表;`frmKeywordList` 收集的是**這個專案已經用過的值** |
| **腳本不能寫標籤** | `Tags` 只有 `Exists` / `Value`,881 支腳本裡沒有任何 setter |

**所以「ACQUA 裡出現一個同步自網頁的下拉選單」技術上做不到。**
打字是唯一的輸入方式 —— 必須靠驗證來補,見 5.0.3。

實證:`ACQUA_auto_v2026Aug` 裡同時存在 `Position=pos1` 和 `Position=POS1`,
正是自由輸入的典型後果。

#### 5.0.2 ⭐ 為什麼語意標籤不夠用(決定性證據)

曾經考慮「不在 ACQUA 存擺位名稱,改用既有的 `Room` / `DUTType` 等語意標籤
對照到擺位」。**實測推翻了這個想法。**

用 `TurningDevices`(ACQUA 自己存的真實轉盤角度)當檢驗:

| 語意組合 | 測項數 | 底下有幾種轉盤角度 |
|---|---|---|
| `Room=AR` | 1092 | **6** |
| `Room=RR` | 470 | **7** |
| (無語意標籤) | 2634 | **4** |
| `Room=RR DUTType=SHAR` | 40 | 2 |

**涵蓋 97% 測項的三大組合,每一個底下都有多種實際硬體配置。**

Speakerphone 專案的狀態數對比:

```
只看語意標籤              12 種狀態 ・ 41 次切換
+ 定位器 HHPSettingName   13 種     ・ 283 次
+ 轉盤角度               24 種     ・ 720 次   ← 真實硬體狀態數
```

**原因不是資料品質不好,是本質問題:**
語意標籤描述的是**測試條件**(在哪個房間、什麼裝置類型),
不是**物理擺位**。同一個房間、同一種裝置,機構可以擺成好幾種樣子。

> 📌 轉盤角度是 ACQUA 自己的欄位。如果 ACQUA 會自動轉(待驗證,
> 見第 8 節),`Setup` 標籤就不必涵蓋轉盤 —— 狀態數會從 24 降到 13。

#### 5.0.3 打字的四道防線

既然只能打字,就要讓錯誤**早點、大聲地**暴露:

**① 開跑前一次驗完,不要跑到才發現**

```
載入測項 → 收集所有 Setup 標籤 → 全部比對擺位清單
   ⚠️ 3 個測項的擺位找不到:
      「RR-共享-1.5」  → 最接近:「RR-共享-1.5m」
      「AR default」   → 最接近:「AR-default」
      「pos1」         → 沒有相近的
   [ 修正後重試 ]  [ 仍要執行 ]
```

跑了兩小時才卡住最糟,所以**最晚不能晚於按下執行的那一刻**。

⚠️ 選「仍要執行」是允許的(見第 8 節的決定),但那些測項會在
**當下的位置**量測 —— 數據可能是錯的。所以防線 ⑤ 不是選配。

**② 模糊比對給建議** —— 差一個字的直接指出最接近的是哪個。

**③ ACQUA 自己會幫一點忙** —— 同一個專案第一次打完之後,那個值會出現在
keyword 清單裡,後面的測項可以挑。**打錯風險集中在每個專案的第一次。**

**④ 網頁改擺位名稱時要擋** —— 這是最大的隱患。改名會讓所有指向它的標籤
失效,而且沒有任何跡象。改名前要查「有幾個測項用這個名字」並警告。
另外需要一支定期跑的同步檢查工具。

**⑤ ⭐ 找不到擺位時,警告要活到最後**

這是「不移動、跳通知、繼續測」這個決定的**必要配套**。

無人值守時沒有人看得到執行中的通知 —— 按下執行就走人了。
一個沒人看到的 toast 等於沒有警告。所以:

```
執行中     找不到擺位 → 不移動滑軌 → 記一筆 → 繼續
                                       ↓
結果紀錄   那幾筆標記「擺位未套用:<名稱>(找不到)」
                                       ↓
跑完摘要   ⚠️ 342 筆完成,其中 12 筆未套用指定擺位
              這些結果可能是在錯誤的位置量到的
              [ 看是哪幾筆 ]
                                       ↓
Word 報告  同樣要帶這個標記(不然交出去的報告看不出問題)
```

**判斷標準:跑完回來只看最後的摘要,要能看出哪幾筆有疑慮。**

> **已實作(2026-10-30)**,見第 2 階段清單。
> 一處要修正原本的設計:Word 報告是 ACQUA 自己產的,內容改不了 ——
> 所以改成另存時在報告隔壁寫一份 `<報告名>.擺位警告.txt`,
> 讓警告跟著檔案一起交出去。

#### 5.0.4 讀取規則(定案 2026-10-16,2026-11-17 加上資料夾繼承)

**只看 `Setup` 標籤的名稱,其他一律不碰。**

```
1. 測項自己有 Setup                     → 用自己的
2. 沒有 → 看同一個資料夾的其他測項:
      只出現一種擺位                    → 用它
      出現兩種以上                      → 不猜,記一筆
      一個都沒有                        → 再往上一層資料夾,同樣規則
3. 一路到專案根部都沒有                 → 沿用當下擺位

名稱找不到對應的擺位                    → 不移動,記一筆,繼續跑
```

**為什麼繼承是看「同資料夾的其他測項」:** ACQUA 介面**不能對資料夾加
標籤**(使用者 2026-11-17 實測)。資料庫也證實:SP2 標了 1858 個測項,
577 個資料夾一個都沒標。所以讓資料夾裡標了的那幾筆代表這個資料夾 ——
實際效果是**每個資料夾標一筆就夠**。那 6% 擺位混雜的資料夾,規則 2
不會亂猜,會要你個別標。

**為什麼不是「沿用上一筆」(照順序往前找):** 順序一變結果就安靜地跟著變,
有人在 ACQUA 裡拖動測項,擺位就換了。用資料夾判斷只跟「在哪個資料夾」有關。

實作:`acqua/setuptags.py` 的 `resolve()`(一次讀整棵專案樹)。
測試:`tools/test_setupflow.py` 第 6 節,每條規則一個案例。

- ACQUA 既有的 `Room` / `DUTType` / `Position` / `TurningDevices` /
  `HHPSettingName` **全部原封不動**,不讀取、不推論、不影響擺位判斷
- 擺位名稱是獨立的一層,跟那些標籤沒有關係

語意標籤唯一的用途是**第 1 階段的盤點工具**拿來建議「哪些測項可能該標」,
人工確認後才下 —— 不參與執行期的任何決策。

實證:`ACQUA_auto_v2026Aug` 裡同時存在 `Position=pos1` 和 `Position=POS1` ——
大小寫不一致,正是自由輸入的典型後果。

#### 改成:用既有的語意標籤 + 我們這端的對照表

```

──────────────────                   ──────────────────────

Room=RR                        →     [ RR-default       ▾ ]
Room=RR DUTType=SHAR           →     [ RR-共享-1.5m     ▾ ]

```

**對照表的規模(實測):**

| 資料庫 | 已標語意標籤的測項 | 相異組合 |
|---|---|---|
| `51_MS_Teams_Rev05_SP2` | 1670 | **12** |
| `51_MS_Teams_Rev05_SP3` | 1670 | **12** |
| `ACQUA_auto_v2026Aug` | 90 | 5 |

12 列的對照表,不是 2302 筆標籤。

#### 這樣解決了什麼

| 需求 | 怎麼滿足 |
|---|---|

| **認證專案** | **一個標籤都不用加** —— 1670 個已經標好了 |

### 為什麼兩個都要

**外部執行器是效率,掛鉤是正確性。**

| | 只有外部執行器 | 加上掛鉤 |
|---|---|---|
| 從我們的網頁跑 | ✅ 正確且有分組最佳化 | ✅ 同上 |
| 有人直接在 ACQUA UI 按執行 | ❌ 擺位錯了照樣跑完 | ✅ 掛鉤補上移動 |
| 外部執行器有 bug 漏移動 | ❌ 靜默產生廢資料 | ✅ 掛鉤補上移動 |

這跟 9 月測出來的「麥克風供電設錯照樣回報 PASS」是同一類問題 ——
**量測系統不會告訴你物理條件錯了。** 掛鉤是唯一能擋在量測真正開始前的位置。

> 💡 我一度以為「掛鉤只能照樹的順序跑所以效率差」—— **那是錯的**。
> 順序是外部執行器決定的,掛鉤只是被動接收。兩者不衝突。

### 3D 介面能不能做進 ACQUA?

**不能重做,但可以叫出來。**

ACQUA 的 Python 沒有 Qt / webview / 3D 引擎,畫不了 WebGL 場景。
但腳本可以:

```python
import webbrowser
webbrowser.open('http://127.0.0.1:5000/soundproofroom')
```

一行,把現成的 3D 頁叫出來,而且永遠跟網頁版同步。
**不建議在 ACQUA 裡重做一套。**

```python
import requests
from ACQUAlyzer import Tags, Smd

SERVICE = "http://127.0.0.1:5000"

def ensure_setup():
    if not Tags.Exists("Setup"):
        return                          # 沒標 = 沿用當下
    want = Tags.Value("Setup")

    # ⚠️ 這裡**不 raise**。第 8 節決定:找不到擺位就不移動、記一筆、繼續。
    #    中斷整晚的批次代價太高,一個打錯的名稱不該讓整批作廢。
    #    代價是那幾筆會在當下的位置量測 —— 所以一定要記錄下來(防線 ⑤)。
    try:
        now = requests.get(f"{SERVICE}/api/room/current", timeout=10).json()
        if now.get("setup") == want:
            return                          # 已經在位置上

        r = requests.post(f"{SERVICE}/api/room/apply",
                          json={"setup_name": want}, timeout=900).json()
        if r.get("ok"):
            return
        note = r.get("error") or "unknown"
    except Exception as exc:
        note = str(exc)

    # 移動失敗 -> 告訴服務記一筆,讓它出現在跑完的摘要與報告裡。
    # 只在 ACQUA 視窗印訊息是不夠的:無人值守時沒有人看得到。
    try:
        requests.post(f"{SERVICE}/api/room/not-applied",
                      json={"smd": Smd.Title, "wanted": want, "reason": note},
                      timeout=10)
    except Exception:
        pass                                # 連記錄都失敗就算了,不能擋住量測
```

## 9. 未來使用者怎麼用

### 日常:什麼都不用做

標籤設好之後,三種跑法都會自動移機構:

```
網頁單批   選專案 → 勾測項 → 執行(命名視窗裡先看到標籤檢查)
網頁序列   排好計畫 → 執行(每一步的說明行先看到標籤檢查)
ACQUA 直接 照平常按執行(專案掛上 HOOK_setup_bridge.py,服務要開著)
                 ↓
   每一筆送出前:需要的擺位跟現在不同 -> 移過去、等到位 -> 才量
   名稱找不到 / 判斷不出來 / 移動失敗 -> 不移動、照常量、記進跑完的摘要
```

**每個資料夾標一筆就夠** —— 沒標的測項會看同一個資料夾裡其他測項的
`Setup`(只有一種就跟著用,兩種以上就不猜、記一筆,都沒有再往上一層)。
ACQUA 不能直接對資料夾加標籤,這是替代做法。

> ⚠️ ACQUA 直接跑的那條路目前**還沒有資料夾繼承** —— 掛鉤只看得到自己那筆
> 的標籤,要等 `Smd.Path` 的格式確認(`HOOK_diagnose_smd.py`)。在那之前,
> 從 ACQUA 直接跑的測項要各自標。

```
② ACQUA → 要用它的測項 → 右鍵 Edit Tags → Setup = <剛才的擺位名稱>
③ 網頁按執行時會自動驗證名稱對不對,打錯會警告並給建議(但不擋,你可以選擇照跑)
```

⚠️ 第 ② 步是**自由輸入**,ACQUA 做不出同步的下拉選單(見 5.0.1)。
所以第 ③ 步的驗證不是選配,是必要的。

同一個專案裡第一次打完之後,那個值會出現在 ACQUA 的 keyword 清單裡,

## 附錄 A:技術速查

### 標籤存哪裡

```sql
SELECT Title, CAST(AdvancedDescription AS nvarchar(max))
FROM acqua.TreeItems
WHERE idTreeItem = 1692
```

格式:

```xml
<Properties>
  <UserDefinedProperties>
    <UserDefinedProperty name="Setup">RR-SHAR-1.5m</UserDefinedProperty>
  </UserDefinedProperties>
  <HRTSettings/>
</Properties>
```

### 腳本存哪裡

```
權威     acqua.Files + acqua.BinData（ZIP 壓縮,開頭 PK)
         FT_Script       = 生命週期掛鉤
         FT_SMDUsedFile  = 單一測項腳本
快取     C:\ACQUA_Files\File_Cache\<專案名>_<GUID>\
```

⚠️ 不要直接改快取(會被覆蓋),也不要直接寫 SQL
(要自己處理 `FileSize` / `CRCValue` / `ChangeDate`)。用 ACQUA 的編輯器。

### 腳本連到測項

```
SMDs.rFileCollection → FileCollectionLists.rFileCollection → Files.idFile
SMDs.idSMDItem == TreeItems.idTreeItem    （同一個 id 空間)
```

樹狀路徑用 `TreeItems.LeftNode` / `RightNode` 的巢狀集合往上爬。

### 腳本可用的 API

```python
from ACQUAlyzer import Smd, Tags, SubProject, MeasObject, ResultFiles, SingleValues
from HEAD import const
from HEAD.AcquaBasic import Results, Variables
from HSL import (run_universal_questionnaire_gui, save_var, get_var_value,
                 get_tag_values, AnalysisDiagram, BGNConfigurator)
import requests, socket, webbrowser, tkinter     # 都可用
```

`ACQUAlyzer` 與 `HSL` 不在檔案系統上 —— ACQUA 執行腳本時注入,
所以腳本只能在 ACQUA 裡跑。

### 我們這端的 API

```
已有   GET  /api/room/setups      擺位清單
已有   POST /api/room/apply       套用擺位到實機
已有   GET  /api/room/axes        軸定義
要加   GET  /api/room/current     現在在哪個擺位
```
