# 聲學測試室 3D 視覺化

three.js + Vite。掛在 Flask 的 **`/soundproofroom`** 路徑下。

---

## 兩種執行方式

### A. 免安裝(現在就能看)

Flask 起來就有:

```powershell
cd ..
.\.venv\Scripts\python.exe app.py
```

開 <http://127.0.0.1:5000/soundproofroom>

這個模式用瀏覽器原生的 **importmap** 從 unpkg CDN 取 three.js,
**不需要 Node、不需要 npm install**。原始碼直接由 Flask 當靜態檔送出。

> ⚠️ 需要連得到網路。離線環境請用下面的 B。

### B. Vite(開發 / 離線)

```powershell
cd soundproofroom
npm install
npm run dev      # 開發伺服器 http://localhost:5173,有 HMR
npm run build    # 打包 → ../static/soundproofroom/
```

**build 完之後 Flask 的 `/soundproofroom` 會自動改用打包好的檔案**(路由會偵測
`static/soundproofroom/index.html` 存不存在),不用改任何設定,也不再需要網路。

## 兩個模式

這一頁有兩個模式,行為差很多 —— 一個碰不到機構,一個一動就是真的動。
所以模式切換放在側欄最上面,而且即時模式整片側欄的底色不一樣。

| | 設定模式 | 即時模式 |
|---|---|---|
| 3D 顯示的是 | 你畫的 | **實機報回來的位置** |
| 拉桿的意思 | 直接改 3D | **提出一個目標**,要確認才移動 |
| 滑鼠拖曳物件 | 可以 | **關閉** |
| 會碰到機構嗎 | 不會 | 會 |
| 主要動作 | 存 / 載入擺位 | 移動單軸 |
| 側欄放什麼 | 擺位的存取按鈕 | **只放狀態與逐軸位置**

預設進**設定模式**。不是預設即時模式的理由:一開頁面就去跟硬體講話、
3D 立刻跳到實機位置,對不預期的人太突然。要直接看實機就帶 `?mode=live`,
切過一次之後會記在 `localStorage`。

**每一次切模式都會先跳確認框**,把「切過去之後拉桿的意思會變成什麼」講一遍;
切到即時模式之前還會先探一次,把「現在到底抓不抓得到實機位置」寫在框上 ——
切過去才發現讀不到,那個資訊來得太晚。

即時模式的側欄**只放狀態與每一根軸的位置**。「把擺位套用到實機」的入口在
擺位詳細頁(`/setups/<id>`),按下去會帶 `?mode=live&apply=<id>` 進來,一樣走
這一頁的確認框 —— 不在一個「按下去機構就會動」的畫面裡再多擺兩個入口。

### 即時模式:為什麼要多問一次

拉桿放手後跳確認框,按確定才下指令。**在按下確定之前,畫面上不會有任何
東西動。**

這不只是「多一道保險」:

- 機構有物理行程,一動就是真的在動。手滑碰到拉桿讓天車跑起來太貴。
- 如果拉桿一動 3D 就跟著動,使用者會以為東西已經移過去了 ——
  那個錯覺比「沒動」危險得多。
- 韌體**沒有中止指令**。送出去就只能等它走完。事後救不回來,唯一的機會
  就是事前講清楚:哪一根軸、從哪到哪、走幾毫米、幾秒、哪一台 Pi、
  送出去的是哪一條指令。確認框上這些全部都寫出來。

所以「停止」那顆鈕寫的是**「停止後續動作」**,不是「緊急停止」——
它只擋得住還沒送出去的軸,正在走的那一段機構會走完。寫成「緊急停止」
會讓人以為按了就會停,那是騙人。真的要立刻停只能斷電。

同一個理由讓「套用整組擺位」是**一根軸一根軸依序**走的:機構的行程互相
重疊(HATS 平台跟升降台就是),同時動撞到了也看不出是誰撞的。

### 位置是怎麼來的

```
Arduino ──Serial──► Raspberry Pi ──HTTP──► 天車控制中心 ──HTTP──► 這裡
                                              (port 5001)        acqua/crane.py
```

`.env` 的 `ACQUA_SETUP_CONTROLLER` 填控制中心的位址就會接實機;**留空就是
模擬位置**。刻意不做「試著連、連不到就退回模擬」—— 連不到的時候要吵,
不要安靜地變成假的。即時模式最上面那一塊會明講現在是哪一種。

#### ⚠️ 機構在動的時候讀不到位置

Pi 的序列埠是單線程的:移動指令會一直佔著埠直到 Arduino 回 `DONE`,
這期間送位置查詢只會排在後面。所以:

| 狀況 | 位置怎麼來 | 面板上 |
|---|---|---|
| 停著 | 真的去問 Arduino | `1.20 m` |
| 移動中 | **由起點、終點、標稱速度推算** | `~1.20 m`(橘色) |

`~` 跟顏色是刻意的:使用者要分得出「量到的」跟「算出來的」,不然會拿推估值
去對現場。查詢指令的助憶碼還沒跟韌體對過(見 `Axis.cmd_query`),對不上時
會一直顯示 `~` —— 系統照樣能用,只是位置一直標成估計。寧願顯示「這個數字
是推算的」,也不要編一個看起來很確定的位置出來。

這件事也決定了 mock 的寫法:**「移動中的位置怎麼算」是寫在基底類別裡、
兩種後端共用的**。`MockCrane` 跟真機的差別只有 `_send_move()` 一個方法
(一個是睡掉該花的時間,一個是發 HTTP)。所以等真機接上來,即時模式的
行為不會忽然變成另一個樣子。

## 擺位(setup)

一個擺位 = 「這一次量測,房間裡每個東西站在哪裡」。存成 `setups/<id>.json`:

```json
{
  "id": "20260915-143052-a3f1",
  "name": "近場 0.5 m ・ HATS 前傾 17°",
  "description": "MS Teams Rev05 用",
  "axes": { "hats.mrp": 1.2, "hats.head": 17.0, "screen.z": 2.05, "...": 0 },
  "source": "setup"
}
```

存放位置預設是專案底下的 `setups/`,可以用 `--setups-dir` 或 `ACQUA_SETUPS_DIR`
換掉。**跑測試一定要指到別的目錄** —— 測試開場會把所有擺位刪光,跟正在用的
服務共用同一個資料夾的話,存好的擺位就沒了(這不是假設,已經發生過一次)。
`GET /api/room/setups` 會回傳目前用的是哪個目錄。

> ⚠️ **`setups/` 有進版控**,跟 `plans/` 一樣 —— 擺位是對過現場才調出來的
> 數字,不是執行期的暫存檔,刪掉重建不回來。存了新擺位記得一起 commit:
> `git add setups/ && git commit -m "setup: ..."`

`source` 分 `setup`(設定模式畫的)與 `live`(從實機讀回來的)—— 清單上
會標出來,因為「這是誰畫的」跟「這是機器當時真的在哪」信心程度差很多。

跟 `plans/` 的測試計畫**刻意分開存**:

| | 存什麼 |
|---|---|
| 測試計畫 | 要跑哪些測項(ACQUA 那一側) |
| 擺位 | 機構擺在哪裡(天車那一側) |

同一個擺位會被好幾個測試計畫共用(「近場 0.5 m」跑三批不同測項),
綁在一起的話改一個位置要去改三個計畫檔。

### ⭐ 軸代號是跨三處的契約

`axes` 的鍵在三個地方是**同一組字串**:

```
soundproofroom/src/main.js   PANEL 裡每個控制項的 id
acqua/crane.py               AXES(對應到哪台 Pi 的哪根軸)
setups/*.json                存好的擺位的鍵
```

因為同名,**存好的擺位可以原封不動送去驅動機構,中間不需要任何對應表**。
這是整個設計裡最關鍵的一個決定。代價是:**改那些 id 會讓存好的擺位對不上**,
要改就得寫搬移。

### 行程為什麼各存一份

`spec.js` 有行程、`acqua/crane.py` 也有。這是刻意重複的 ——
後端絕對不能拿瀏覽器送來的範圍當行程上限,不然改一個數字就能把機構送去
撞牆。但重複不能是靜悄悄的:即時模式啟用時會去 `/api/room/axes` 對一次,
不一致就在側欄跳紅字,並說明實際以後端為準。

## 頁面與 API

| 網址 | 做什麼 |
|---|---|
| `/soundproofroom` | 3D 頁 |
| `/soundproofroom?mode=live` | 直接進即時模式 |
| `/soundproofroom?setup=<id>` | 設定模式 + 載入那個擺位 |
| `/soundproofroom?mode=live&apply=<id>` | 即時模式 + 跳出「要套用嗎」的確認框 |
| `/setups` | 擺位清單(一排直的,一頁十個) |
| `/setups/<id>` | 單一擺位:左邊軸名、右邊數字,可以直接改再存 |

| API | 做什麼 |
|---|---|
| `GET /api/room/live` | 每根軸的位置 + 移動作業 + 裝置狀態(移動中 350 ms、閒置 1.8 秒打一次) |
| `GET /api/room/axes` | 軸清單與行程,用來跟 `spec.js` 交叉比對 |
| `POST /api/room/move` | 移動單軸 `{axis, target}` |
| `POST /api/room/apply` | 套用一整組 `{setup_id}` 或 `{axes}`,依序移動 |
| `POST /api/room/stop` | 取消還沒送出去的軸(回應帶 `partial: true`) |
| `GET|POST /api/room/setups` | 清單 / 新增 |
| `GET|POST|DELETE /api/room/setups/<id>` | 詳細(存檔的值 + 軸定義) / 更新 / 刪除 |

`/api/room/live` 讀的是背景執行緒維護的快取,所以很快。**不是**每次請求都去
問 7 台 Pi —— 那是 7 次 HTTP 來回,前端每秒刷一次的話請求會越積越多
(天車控制中心的 README 記過同一個坑)。

後端不信任前端:`move` 與 `apply` 的目標值在 `bridge.submit()` 裡會再夾一次
行程,同一時間也只允許一個移動作業。前端那個確認框是給人看的,不是安全機制。

## 還沒接上的部分

- **`pi-001` ~ `pi-007` 跟哪個總成配對要照現場接線對一次**
  (`acqua/crane.py` 的 `AXES`,標了 `[待確認]`)。一台 Pi = 一組天車 =
  一個可動總成;改接線只改那張表,其他程式碼一行都不用動。
- **位置查詢的助憶碼**(`Axis.cmd_query`,現在推成 `<軸>P`)。對不上時
  韌體回 `ERR`,位置就一直標成估計值 —— 不會壞,只是不準。
- **標稱速度**(`Axis.speed`)只用來算預估時間與移動中的估計位置,
  不會送給韌體。對現場量一次會讓預估準很多。

## 改尺寸

**只改 `src/spec.js`。**

```
spec.js   ⭐ 規格尺寸   房間、行程、設備尺寸、預設高度
look.js      外觀       顏色、材質、燈光、相機
   └─────────┬─────────┘
        config.js       合併成 CONFIG,本身一個數字都沒有
             ↓
   builders.js / main.js
```

分兩份的理由:規格數字要拿去對現場、會被人問「這 0.42 哪來的」,所以得能單獨
攤開來看。顏色不會。混在一起的話,改尺寸時要在一堆 `0x9aa3ad` 中間找 `0.42`。

`spec.js` 裡每個數字都標了來源:

| 標記 | 意思 |
|---|---|
| `[規格]` | 設備原廠規格書 / 測試規範明確寫的 |
| `[圖面]` | 現場圖面標註的 |
| `[推估]` | ⚠️ 圖面沒標、依比例抓的,對照現場要調 |
| `[構造]` | 模型結構件(底座、滑車、托座),照片目測 |

### 陣列驅動

重複性的物件是陣列驅動的:

```js
tables: { items: [ {key,label,lift,travelZ}, ... ] }
micRig: { items: [ {key,label,travelX,travelZ,heightDefault}, ... ] }
```

**在陣列裡多加一筆,3D 物件與側邊欄控制項都會自動生出來** —— 不用改
builders 也不用改 HTML。

### 座標系

three.js 慣例,Y 朝上,原點在房間正中央地板:

```
X = 寬 3.41   Y = 高 2.35   Z = 深 5.20
喇叭陣列在 -Z 端,大螢幕在 +Z 端(兩者相對)
```

### builders.js 裡還有數字嗎

有 94 個,但**都不是尺寸**:材質的 roughness / metalness、避免 z-fighting 的
0.002 位移、`Math.max(0.05, ...)` 這種防止幾何翻面的保護值,以及會自己跟著
spec 縮放的相對比例(例如「端塊是滑軌的 2.2 倍粗」)。

拉出來的是 **27 處絕對尺寸**:HMS II.3 托座 0.20×0.05×0.16、桌子底盤 0.46、
螢幕底座 0.62×0.42、吊車 0.16×0.08×0.13、耳部麥克風 Ø0.024、脖子長度 0.07⋯
這些以前寫死在 builders.js,改 config 改不到。

## 操作

| 動作 | 結果 |
|---|---|
| 左鍵拖**物件** | 移動該物件(各自限制在自己的行程內)—— **只有設定模式** |
| 左鍵拖**空白處** | 旋轉視角 |
| 滾輪 / 右鍵拖曳 | 縮放 / 平移 |
| 側邊欄 slider | 設定模式:精確定位,與拖曳雙向同步<br>即時模式:提出移動目標,放手後跳確認框 |

側邊欄是**依 config 動態生成**的 —— 物件多了之後,靜態 HTML 很容易漏掉控制項。

拖曳支援單軸與雙軸(`axes: { x, z }`),HATS 與麥克風吊架的 X 軸會套用到
**子層滑塊**而不是整組,層級關係跟實體機構一致。

## 已知限制

- **HATS 是簡化幾何**(方塊軀幹 + 球頭 + 耳/嘴標記),尺寸依 B&K 4128 規格但
  不是原廠 3D 模型。要換真模型在 `buildHats()` 改用 `GLTFLoader`。
- ⚠️ **標「推估」的位置**:滑軌在房間內的確切座標、橫移軌長度、螢幕尺寸與
  擺放。圖面只標了長度沒標中心座標,對照現場調 `spec.js` 即可。
- 前/後桌台我對應到規格的 **DUT / Dixie 兩台升降台**(0.80×0.80 的尺寸與位置吻合)。
